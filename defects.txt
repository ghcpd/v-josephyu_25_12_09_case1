DEFECT #1: Incorrect Virtual Environment Activation Path
---------------------------------------------------------------------
Location: Section 3.1 - "Create and Activate Virtual Environment (Windows PowerShell)"
Severity: HIGH

README States:
  .\\.venv\\Scripts\\Activate.ps1

Actual Implementation:
  .\.venv\Scripts\Activate.ps1

Issue: The README shows escaped backslashes (\\) which is incorrect for PowerShell. 
The actual command should use single backslashes (\).

Reproduction Procedure:
  1. Follow README section 3.1 exactly
  2. Command: .\\.venv\\Scripts\\Activate.ps1
  3. Expected: Virtual environment activates
  4. Actual: PowerShell treats the escaped backslashes literally, causing errors

Error Trace:
  PS> .\\.venv\\Scripts\\Activate.ps1
  # This tries to find a directory literally named "\.venv\Scripts\Activate.ps1"

Fix: Use .\.venv\Scripts\Activate.ps1 (single backslashes)


DEFECT #2: Command-line Arguments Not Supported
---------------------------------------------------------------------
Location: Section 3.3 - "Start the App"
Severity: HIGH

README States:
  python app.py --host=0.0.0.0 --port=8080

  Default behavior:
  - Binds to `http://0.0.0.0:8080/` in this configuration
  - Command-line flags `--host` / `--port` can be used to change the bind address and port

Actual Implementation in app.py:
  if __name__ == '__main__':
      app.run(debug=True)

Issue: The app.py code does NOT parse or handle --host and --port command-line arguments.
The app.run() method is called without any parameters, so it will always use default 
Flask settings (127.0.0.1:5000).

Reproduction Procedure:
  1. Follow section 3.3 exactly
  2. Run: python app.py --host=0.0.0.0 --port=8080
  3. Check the output
  4. Actual result: "Running on http://127.0.0.1:5000"
  5. Expected: "Running on http://0.0.0.0:8080"

Error Trace:
  $ python app.py --host=0.0.0.0 --port=8080
   * Running on http://127.0.0.1:5000
  
The --host and --port arguments are silently ignored by Python.

Fix: Either:
  A) Remove these arguments from README documentation
  B) Update app.py to parse command-line arguments:
     
     import argparse
     if __name__ == '__main__':
         parser = argparse.ArgumentParser()
         parser.add_argument('--host', default='127.0.0.1')
         parser.add_argument('--port', type=int, default=5000)
         args = parser.parse_args()
         app.run(host=args.host, port=args.port, debug=True)

DEFECT #6: Misleading Session Configuration Documentation
---------------------------------------------------------------------
Location: Section 4.3 - "Sessions & Login"
Severity: MEDIUM

README States:
  - Uses `Flask-Login` to manage user login state.
  - Login view name: `auth.login`, mapped to `/login`.
  - Sessions are stored server-side in Redis for better scalability.
  - A local in-memory fallback session store may be used for development if Redis 
    is not configured.

  To run the app in stateless API-only mode without sessions, set `SESSIONLESS_MODE=true` 
  in your environment before starting `app.py`.

Actual Implementation:
  The code does NOT use Redis. Sessions use Flask's default session mechanism 
  (signed cookies). No Redis configuration exists. The SESSIONLESS_MODE environment 
  variable is not checked or used anywhere in the code.

Issue: The README describes configuration that doesn't exist and contradicts the 
actual implementation.

Reproduction Procedure:
  1. Start the app without setting up Redis
  2. Try to use the app normally
  3. Expected (per README): Should fail without Redis or use in-memory fallback
  4. Actual: App works fine without Redis

Error Trace:
  No Redis errors occur. The app uses standard Flask sessions instead.
  SESSIONLESS_MODE environment variable has no effect.

Fix: Update README section 4.3:
  - Uses `Flask-Login` to manage user login state.
  - Login view name: `auth.login`, mapped to `/login`.
  - Sessions are stored using Flask's default session mechanism (signed cookies).
  - No additional session backend configuration is required.
