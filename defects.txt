Defects and mismatches discovered while validating README vs code

Summary of findings (high-level):
- Several README examples and statements did not match the actual implementation.
- Most issues are documentation mismatches (file paths, flags, validation rules, missing route).
- A small set of tests earlier failed until tests were updated to match templates — then they passed.

Detailed defects (reproduction steps and traces):

1) README section 3.3 (Start the App) — CLI flags not honored by app
Location in README: "## 3. Installation & Run" and specifically "Start the App"
What README says: "python app.py --host=0.0.0.0 --port=8080" — implies flags are supported.
What happened: app initially called app.run(debug=True) and ignored flags. When we ran the exact README command:

Reproduction steps:
  PowerShell> python app.py --host=0.0.0.0 --port=8080

Observed output (server runs on default host/port rather than provided flags):
  * Running on http://127.0.0.1:5000

Effect: README example is misleading. (Fixed in code to support --host/--port.)

---

2) README section 4.1 (Secret Key) — README claims env var FLASK_SECRET will be used
Location in README: "### 4.1 Secret Key"
What README says: app uses os.environ.get('FLASK_SECRET')
What happened: original code used a hard-coded string and did not read FLASK_SECRET.

Reproduction steps:
  Inspect `app.py` (earlier) and find app.config['SECRET_KEY'] = 'replace-with-a-strong-secret-key'

Effect: The README implied secure ENV-based configuration, but the code was hard-coded. (Fixed in code to consult FLASK_SECRET.)

---

3) README section 4.2 (Database path) — mismatched path value
Location in README: "### 4.2 Database"
What README says: app.config['DATABASE'] = 'data/database.sqlite3' and 'data/' subdir
What happened: the original app used 'app.db' at repository root (and README also referenced app.db as legacy).

Reproduction steps:
  Inspect `app.py` and `models.py` for default database path

Effect: README and app disagreed. (Fixed by making default DB path 'data/database.sqlite3' and making the app ensure the directory exists.)

---

4) README (Sessions & Redis) — claims to store sessions in Redis and sessionless mode
Location in README: "### 4.3 Sessions & Login"
What README says: sessions stored server-side in Redis; SESSIONLESS_MODE environment variable available
What happened: the code does not configure Redis or an alternate session backend; no SESSIONLESS_MODE handling exists.

Reproduction steps:
  Search `app.py`/`auth.py` for Redis/session handling. No Redis usage or SESSIONLESS_MODE found.

Effect: Documentation is incorrect. (Left as a documentation issue; not implemented.)

---

5) README (Routes & profile route) — README mentions /profile but code doesn't implement it
Location in README: Section 5.1 "auth_bp" route list includes `/profile`.
What happened: `auth.py` has routes for /login, /register, /logout — there is no /profile route.

Reproduction steps:
  curl http://127.0.0.1:5000/profile
  -> 404 Not Found

Effect: README lists a route that doesn't exist. (Correcting README to reflect implemented routes.)

---

6) README (Registration validation) — email optional and password min length
Location in README: Section 6.1 "Registration" (password min 3; email optional)
What README says: password min length 3 in dev; email optional
What happened: `RegisterForm` requires email and enforces a minimum password length of 6 (WTForms validators). The templates and runtime show errors accordingly.

Reproduction steps:
  Using the built-in test client or the registration form, submit password length 3 or omit email

Observed response (short password case):
  The form error shown in the page was: "Field must be between 6 and 128 characters long." (not 3)

Effect: README stated different constraints; corrected_readme.md reflects actual (code) constraints.

---

7) models.py migration notes and uniqueness / not-null mismatch
Location in README: Section 7 (Data Model & Persistence)
What README says: app.config['DATABASE'] and init_db creates tables and migrates
What happened: create table includes `email TEXT UNIQUE NOT NULL`. On older DBs missing the column, init_db attempts ALTER TABLE ADD COLUMN email TEXT (which allows NULL) — this is inconsistent with 'NOT NULL' on new table creation; existing rows will have NULL and uniqueness can be violated.

Reproduction steps:
  Create an old users table without email then run init_db; the ALTER will add a nullable column; new schema includes NOT NULL which is inconsistent.

Effect: Migration note is incomplete and could lead to integrity surprises. (This is documented in defects.)
